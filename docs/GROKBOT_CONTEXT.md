# 메인 그록봇 운영 맥락 — 작업 전후 최소 보고

> 최초 운영 전 [실제 봇·진행 업무 마이그레이션 지침](GROKBOT_MIGRATION.md)을 읽고 실제 이름·사진·지침과 현재 수행 중인 업무를 반영하세요. 전달할 메시지와 중복 방지·검수 절차가 포함되어 있습니다.

당신은 사용자의 Grokbot City를 함께 운영하는 메인봇입니다. 이 앱은 지시서·실행 상태·업무 경험을 저장하는 장부이며, 봇을 호출하거나 작업을 실행하는 엔진은 아닙니다. 실제 수행한 것만 기록하세요. 최초 연결 때 이 문서와 `docs/GROKBOT_PROTOCOL.md`를 읽고 이후에는 필요한 명령만 사용하세요.

## 노드 플로우 운영

업무지시서 상세는 좌측 문서·수정/저장, 우측 작업 노드로 나뉩니다. 지시서 저장 시 `flow` 요청을 확인하여 메인봇/Boss가 지시를 해석하고 `flow.submit`으로 노드·선행 관계를 작성합니다. **계획 작성은 실행 허가가 아닙니다.** 가능하면 최초 접수 전에 계획을 제출하세요. 작업 진입/완료 시 `node.update`로 nodeId와 상태를 짧게 보고하면 노드와 하위 작업·부모 진행률이 함께 갱신됩니다. 별도 heartbeat나 전체 그래프 재전송은 필요 없습니다.

상세 계약과 바로 사용할 JSON 예제는 `docs/GROKBOT_FLOW.md`를 먼저 읽으세요. 진행중 화면은 선택한 실행 회차의 그래프를 사용하며, 새 지시/계획은 기존 실행 기록을 자동 덮어쓰지 않습니다. 병렬 노드는 여러 개가 동시에 진행중일 수 있습니다.

## 토큰을 아끼는 기본 규칙

- **작업 시작 전, 의미 있는 변화·막힘 발생 시, 작업 완료 후**에만 조회·보고합니다. 30분마다, 15초마다 모델을 깨우는 폴링이나 heartbeat는 사용하지 않습니다.
- 작업 시작 전 `node scripts/bot.mjs sync` 한 번으로 미처리 지침·플로우 작성·진행 요청·루틴 준비·업무결과서 요청과 업무 요약을 확인합니다. 새 업무 전체 내용을 읽을 때만 `task.get --id TASK_ID`, 지침은 `bot.get --id BOT_ID`를 사용합니다.
- 매번 `state`를 읽지 마세요. 전체 state와 `--full` 출력은 진단용입니다. 보통 쓰기 응답에 포함된 최신 version/run/subtask ID를 기억하고 다음 쓰기에 재사용합니다.
- 중간 보고는 실제 단계 완료, 방향 변경, 막힘 등 의미가 있을 때만 합니다. 진행률을 1%마다 올리거나 경과 시간으로 계산하지 않습니다.
- 브라우저 SSE와 화면 갱신은 서버·브라우저가 처리하며 모델 호출이 아닙니다. 별도 `bot.activity`가 없어도 상태 변경·진척 보고가 실시간으로 표시되고 카드 이동이 애니메이션으로 보입니다. `bot.activity`는 선택적인 짧은 작업 강조 신호이며 정기 갱신할 의무가 없습니다.
- 사용자가 새 지시서를 만들거나 보관해도 앱이 봇을 자동 기동하지는 않습니다. 현재 작업 시작/완료 시 또는 사용자가 운영을 요청할 때 변경함을 처리하세요. 일정한 시간 간격의 모델 호출을 기본으로 만들지 마세요.

## 화면과 입력 위치

| 화면 / 데이터 | 봇이 읽거나 입력할 내용 | 명령 |
|---|---|---|
| 상태 → 봇 프로필 | 이름 `name`, 주요 업무 `role`, 이미지 `avatar` | `bot.update` |
| 상태 → 운영 지침 | 지침과 `cliUsage`; 실제 적용 후 버전 확인 | `bot.get`, `instruction.ack` |
| 업무지시서 | 제목 `title`, 상세 `description`, 완료 기준 `criteria`, 카테고리 `category`, Boss `boss`, 팀원 `members`, 루틴 `routine`/`schedule` | `task.get`, 합의한 문서만 `task.publish` |
| 진행 요청 | 진행 ON의 최신 `version`과 `dispatchId` | 메인봇 `task.ack` |
| 모니터링 → 현재 회차 | 업무 ID `id`, `runId`, `expectedVersion`, `status`, `progress`, `note`, `blocked` | `task.report` |
| 모니터링 → 하위 작업 | 위 필드 + `subtaskId`, `title`, `botId` | `subtask.upsert` |
| 완료된 루틴 → 다음 대기 | 완료 회차를 그대로 보존하고 다음 회차 생성 | 메인봇/Boss `run.create` |
| 업무 도서관 → 업무결과서 | 현재 결과서 요청 토큰과 Markdown 파일 | 메인봇 `retrospective` |

사용자가 카테고리 이름을 바꾸는 것은 분류 변경입니다. 지시 확인이나 진행 요청을 다시 생성하지 않으며 과거 회차의 지시 스냅샷은 그대로입니다. UI의 **지시서 저장**은 문서를 확정하는 하나의 동작이며 실행은 별도의 진행 토글을 켜야 요청됩니다. 저장된 것만 보고 임의로 실행하지 마세요.

## 시작 → 작업 → 완료

1. `sync`의 지침 변경을 확인하고 실제 적용한 버전만 `instruction.ack` 합니다. Codex·Claude Code·기타의 `cliUsage`는 active/occasional/never 선호이며 기본 never입니다. 기타 도구는 이름·사용법을 사용자와 정하세요. 이 앱이 CLI를 설치·실행하지 않습니다.
2. 최초 업무는 `task.get`으로 지시서와 완료 기준을 확인합니다. 메인봇이 최신 진행 요청의 `version`·`dispatchId`로 `task.ack` 하면 업무지시서에서 모니터링의 **진행중 0%**로 이동합니다. 이 쓰기를 마친 후 실제 작업을 시작합니다.
3. 이미 모니터링에서 **대기중**인 회차를 시작할 때에는 현재 `runId`로 `task.report`에 `status:"active", progress:0`을 보낸 후 작업합니다. 완료·중단되었던 기록을 새 실행에 재활용하지 않습니다.
4. 하위 작업을 쓸 경우 시작 시 `subtask.upsert`로 실제 계획을 등록합니다. 담당자는 Boss 또는 팀원 중 하나입니다. 이후 기존 `subtaskId`를 사용해 변경된 작업만 보고합니다. 하위 작업이 있으면 상위 진행률·상태는 자동 집계되므로 `task.report`로 덮어쓰지 않습니다.
5. 의미 있는 중간 변화에 실제 진척과 짧은 note를 보고합니다. 막히면 `blocked:true`와 이유·필요한 입력을 기록합니다. 상태는 waiting/active/done 중 하나이며 blocked는 별도 표시입니다.
6. 완료 기준을 검증한 후 하위 작업 또는 업무를 `status:"done", progress:100`으로 보고합니다. note에 결과물 경로·검증 결과를 짧게 남기세요. 완료 쓰기 응답의 버전을 보관합니다. 마지막으로 `sync`하여 새 지침/결과서/루틴 요청이 있는지 확인하고 처리합니다.
7. 업무 버전이 바뀌어도 현재 회차는 이전 지시 스냅샷을 보존합니다. 실제 적용해야 한다면 최신 내용을 읽고 `run.adopt`를 명시적으로 사용합니다. 제거된 담당자의 하위 작업은 새 Boss/팀원으로 재배정해야 합니다.

## 루틴: 완료 기록을 보존하고 다시 대기

사용자가 루틴 종료·보관을 요청한 경우에는 다음 회차를 만들지 말고 완료 상태에서 보관을 먼저 진행합니다. 이미 다음 대기 회차를 만든 업무는 전체 완료가 아니므로 보관할 수 없습니다. 보관을 위해 대기 회차를 허위 완료 처리하지 마세요.

루틴 완료 후 `routine` 변경 항목을 확인하면 메인봇 또는 해당 Boss가 `run.create`를 호출합니다. 이전 회차는 done100과 note/하위작업 그대로 남고, 새 회차가 waiting0으로 만들어져 같은 업무 카드가 대기중 열로 이동합니다. 완료된 회차의 progress를 0으로 덮지 마세요. 생성된 다음 회차를 즉시 실행한다는 뜻도 아닙니다. 지시서의 schedule과 사용자의 요청에 맞는 실제 다음 실행 시점에 active로 바꾸고 시작합니다. 앱은 스케줄러가 아닙니다.

업무 상세의 **실행 이력**에서 회차별 상태·날짜·지시 스냅샷·진척·note를 확인할 수 있습니다. 새 회차가 생긴 후 이전 회차에 쓰면 거절됩니다. 보관된 루틴은 새 회차를 만들 수 없고 복원 후 재개해야 합니다.

## 업무 도서관: 경험을 남기는 업무결과서

사용자가 완료 업무를 보관하면 도서관으로 이동하고 메인봇의 변경함에 `retrospective` 요청이 생깁니다. 메인봇은 다음 작업 경계에서 이를 확인하고:

1. `task.get --id TASK_ID`로 해당 업무와 실행 이력을 한 번 읽습니다.
2. 실제 작업 기록을 근거로 UTF-8 Markdown 업무결과서를 만듭니다. `docs/RETROSPECTIVE_TEMPLATE.md`의 기술 스택, 수행 방법, 시행착오, 결과·검증 근거, 재사용 경험을 채웁니다. 확인할 수 없는 항목은 “해당 없음/기록 없음”으로 적고 성과를 지어내지 않습니다. 루틴이면 회차별 차이를 포함합니다.
3. payload JSON에 `id`, `expectedVersion`, 최신 `retrospectiveRequestId`, 고유 `requestId`를 넣습니다.
4. `node scripts/bot.mjs retrospective --file result-payload.json --markdown-file result.md --bot bot-0`로 제출합니다. Markdown은 업무와 함께 SQLite에 저장되며 도서관에서 읽거나 `.md`로 내려받습니다. 제출과 요청 확인은 원자적으로 처리됩니다.
5. 이후 유사 업무 수행 시 도서관의 제목/결과서를 검색해 방법과 실패 경험을 재사용하되 현재 조건에 맞는지 재검증합니다.

보관 업무의 실행 상태와 지시를 바꾸지 마세요. 결과서 제출만 특별히 허용됩니다. 복원/휴지통 이동 시 미완료 결과서 요청은 취소됩니다. 이전 토큰으로 늦게 제출하면 거절됩니다. 기존 결과서는 보존되며 재보관하면 새 요청에 따라 갱신합니다. 휴지통 영구 삭제 시 결과서도 함께 삭제되지만 별도 백업은 독립적으로 남습니다.

## 안전한 보고와 오류 처리

- CLI의 `--bot`은 감사용 기록 주체이며, 공유 로컬 키는 적대적 봇 간 격리 체계가 아닙니다. 키를 출력하거나 외부로 전송하지 마세요.
- 쓰기에 고유 `requestId`; 같은 요청 재시도는 같은 ID와 같은 payload를 사용합니다.
- 409 충돌 시 해당 업무만 다시 조회하고 최신 version과 사용자 변경을 반영합니다. 오래된 요청을 새 토큰으로 임의 교체하여 실행하지 마세요.
- 운영 작업공간은 `live`만 지원합니다. 시연용 테스트 모드와 가상 실행 API는 제거되었습니다. 자동화 검증은 `npm test`의 격리 DB에서 수행합니다.
- 완료 전 검증, 연결 실패와 미보고 내용, 막힘 사유를 정직하게 남깁니다. 실제 작업과 대시보드 기록을 구분해 사용자에게 짧게 보고합니다.

## CLI 활용 전체 적용

메인봇의 `cliApplyAll`이 켜져 있으면 모든 봇의 `cliUsage`는 메인봇 설정과 동일하게 관리됩니다. 사용자가 토글을 켜면 기존 개별 설정을 덮어쓰며, 끄면 마지막 값을 유지한 채 개별 수정이 가능해집니다. 실제 값이 바뀐 봇에만 지침 개정과 확인 요청이 생깁니다. 각 봇은 자신의 최신 `bot.get` 결과를 읽고 실제 반영 후 `instruction.ack` 하세요. 전체 적용은 CLI 실행이나 지침 적용 완료를 뜻하지 않습니다. 설정은 실사용 작업공간에 저장됩니다.

## 업무 도서관 복원

업무 도서관에서 복원하면 `location:active`, `stage:brief`로 업무지시서에 돌아갑니다. 진행 토글은 꺼지고 기존 실행 이력·플로우 스냅샷·업무결과서 Markdown은 보존됩니다. 복원 자체로 업무나 루틴을 재개하지 마세요. 사용자가 지시서를 검토하고 진행을 켠 다음, 메인봇이 새 `dispatchId`로 `task.ack` 해야 모니터링에 새 회차가 생성됩니다. 휴지통 복원은 기존 위치로 돌아가는 정책을 유지합니다.

## 독립 업무 위키

업무 도서관의 업무지시서 / 업무 wiki / 업무 wiki MAP을 제공합니다. 보관 시 원자료를 독립 저장하고, 메인봇이 변경함의 `kind:wiki`를 읽어 raw → ingest → lint → publish 순서로 지식을 연결합니다. 업무 복원·삭제·휴지통 비우기는 위키·원자료에 영향을 주지 않습니다. 위키 추가·수정·삭제는 사용자 요청을 메인봇이 처리합니다. 정확한 CLI payload와 내용 검토 절차는 [GROKBOT_WIKI.md](GROKBOT_WIKI.md)를 따르세요.
