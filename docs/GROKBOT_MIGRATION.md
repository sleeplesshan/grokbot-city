# 실제 그록봇 마이그레이션 지침

## 메인봇에게 전달할 메시지

Grokbot City를 실제 운영 정보로 채워 주세요. 먼저 `docs/GROKBOT_CONTEXT.md`, `docs/GROKBOT_PROTOCOL.md`, `docs/GROKBOT_FLOW.md`와 이 문서를 읽어 주세요. 실제 그록봇 설정에서 메인봇과 추가 봇들의 이름, 사진, 역할, 지침을 확인해 대시보드에 반영해 주세요. 현재 수행 중인 업무도 빠짐없이 조사하여 담당자, 업무 흐름, 현재 단계와 실제 진행률을 모니터링에 반영해 주세요. 가상의 예시나 추정한 완료율을 실제 정보처럼 넣지 마세요. 기존 대시보드 항목과 대조해 중복 없이 이관하고, 확인할 수 없는 정보는 사용자에게 알려 주세요. 실사용 작업공간에서 작업하되 기존 데이터와 완료 이력은 보존하세요.

## 1. 기존 정보 대조

- `node scripts/bot.mjs sync --workspace live`와 `bot.list`로 현재 대시보드 정보를 확인합니다. 필요한 업무만 `task.get --id ID`, 봇만 `bot.get --id ID`로 읽습니다.
- 실제 그록봇 설정에서 접근 가능한 프로필, 지침, 진행 중 업무와 산출물 근거를 읽습니다. 접근 권한이 없으면 필요한 원본을 요청하고 임의로 만들어 넣지 않습니다.
- 실제 봇과 슬롯의 대응표를 작성합니다. 메인봇은 `bot-0`이며 기존 추가 봇 ID는 바꾸지 않습니다. 초기 `bot-1`~`bot-6`은 시작용 슬롯일 뿐 개수 제한이 아닙니다. 기존 대응과 빈 슬롯을 확인해 재사용하고, 부족하면 메인봇이 `bot.create`로 실제 봇을 필요한 만큼 추가합니다. 서버가 반환한 새 ID를 사용하고 직접 번호를 지정하지 마세요. 기존 매핑이 모호한 경우만 사용자에게 확인합니다. 남는 슬롯에는 가상 프로필을 넣지 않습니다.
- 동일 업무의 제목뿐 아니라 목표, 담당자, 산출물을 비교하여 기존 항목을 재사용합니다. 도서관/휴지통의 항목을 자동 복원하거나 재실행하지 않습니다.

### 부족한 슬롯 추가

`docs/GROKBOT_PROTOCOL.md`의 `bot.create` 예제를 따릅니다. 실제 봇마다 고유한 `requestId`를 사용하고, 같은 요청의 재시도에는 같은 ID와 같은 payload를 사용하세요. 성공 응답의 `result.id`를 대응표에 저장합니다. 작업을 다시 시작할 때는 먼저 `bot.list`와 대응표를 대조하세요. 새 요청 ID로 같은 봇을 다시 등록하면 별도 봇이 생성될 수 있습니다. 이름은 영구 식별자가 아닙니다.

초기 슬롯 숫자를 수정하거나 DB를 초기화하지 마세요. 기존 DB에서 추가 명령을 실행하면 기존 봇·업무·이력을 유지하면서 확장됩니다. 대시보드에 새 봇과 개수가 실시간 반영됩니다.

## 2. 실제 프로필과 지침 반영

`bot.update`에 `id`, 최신 `expectedVersion`, 실제 `name`, `role`, `avatar`를 넣습니다. 사진은 실제 봇에 설정된 이미지를 사용하고 이미지 생성으로 대체하지 않습니다. 파일을 Git에서 제외된 `public/assets/local/` 아래 고유한 이름으로 저장하고 `avatar`에는 `/assets/local/파일명`을 넣습니다. 외부 URL이나 인증 정보를 저장하지 않습니다. 파일 추가 후 `npm run build`로 서비스 자산에 반영합니다. 사진 원본이 없으면 기본 아바타를 유지하고 누락 사항을 보고합니다.

실제 운영 지침은 `instruction.publish`로 게시하고, 각 봇이 실제 반영한 버전만 `instruction.ack` 합니다. CLI 선호도와 전체 적용 정책은 사용자 설정을 유지하며 이관을 이유로 임의 변경하지 않습니다. 작업마다 응답의 새 버전을 사용합니다.

## 3. 현재 수행 중 업무를 모니터링에 반영

새 업무는 `task.publish`로 제목·설명·완료 기준·카테고리·개인/팀 구분·Boss·팀원을 실제 정보대로 등록합니다. 설명에 이관 일시와 기존 업무 식별 정보, 현재까지의 수행 근거를 짧게 기록합니다. 팀원은 Boss 제외 최대5명입니다.

1. `flow.submit`으로 실제 업무 단계를 노드와 연결로 등록합니다. 정확한 필드는 `GROKBOT_FLOW.md`를 따르며 노드 ID는 이후에도 유지합니다.
2. 이번 사용자의 요청은 **이미 진행 중인 실제 업무를 이관**하는 범위에 한해 진행 등록을 허용합니다. 해당 업무의 `task.dispatch`를 enabled:true로 보내고 새 `dispatchId`와 게시 버전으로 메인봇이 `task.ack` 합니다. 미착수 계획은 업무지시서로 남기며 임의 시작하지 않습니다.
3. 반환된 새 `runId`를 사용하여 `node.update`로 완료한 단계, 현재 작업 중인 단계, 대기 단계를 각각 반영합니다. 실제 확인 가능한 진행률을 넣고 불명확하면 active/0과 짧은 설명을 사용합니다. 완료는 검증 근거가 있을 때만100으로 표시합니다. 부모 진행률은 노드에서 자동 집계됩니다.
4. 기존 모니터링 업무는 현재 회차를 재사용합니다. 기존 보고를 덮어쓰거나 새 회차를 중복 생성하지 않습니다. 기존 플로우 없는 보고를 새 노드로 임의 변환하지 말고 기존 `task.report`/`subtask.upsert` 방식과 흐름 적용 제약을 따릅니다.
5. 과거 시작 시각을 현재 접수 시각으로 오해하지 않도록 설명이나 note에 원래 시작일을 기록합니다. 앱 이력은 이관 시각 기준이며 과거 작업 로그를 허위 생성하지 않습니다.

## 4. 검수와 이후 운영

- 실제 명단 ↔ 슬롯 대응, 사진 표시, 지침 버전, 진행 중 업무 수, 담당자, 현재 노드와 상태를 대조합니다.
- 사용자에게 이관된 봇/업무, 재사용한 기존 항목, 누락·불확실한 항목을 짧게 보고합니다. 이 문서는 지침이며 자동 마이그레이션이 실행되었다는 의미가 아닙니다.
- 이후 업무 시작 전·단계 전환·막힘·완료 시에만 짧은 갱신을 보냅니다. 주기적인 모델 호출 대신 대시보드 SSE가 화면 갱신을 담당합니다.
- 헤더는 실사용 작업공간의 전체 현황입니다. 봇 상태의 현황은 선택한 봇이 최신 회차의 Boss 또는 팀원인 업무와 해당 봇에게 온 확인 요청입니다. 복원된 지시서는 모니터링 수치에 포함되지 않습니다.
